# 代码变更影响分析

目标读者：要判断发版风险、安排回归或写发布说明的人。回答**对外和下游发生了什么变化**，不是做代码走读。

## 1. 锁定范围并读透改动

- **优先用用户指定的范围**：分支对比（`main...HEAD`）、提交区间（`HEAD~5..HEAD`）、tag、PR 基线、指定提交或暂存区（`git diff --cached`）。
- **未指定范围时**：先定位 Git 仓库根目录（不在 Git 仓库中直接说明），跑 `git status --short --untracked-files=all`。
  - 工作区有改动：默认以 `HEAD` 为基线、当前工作区为新版（`git diff --stat HEAD` + `git diff HEAD`，未跟踪的新文件直接读内容）。暂存与未暂存相互抵消时按最终状态算；首次提交前以空仓库为基线。
  - 工作区干净：不要凭空推测。直接说明工作区无未提交改动，并列出最可能的候选范围（如未推送提交 `@{u}..HEAD` 或最近一次提交 `HEAD~1..HEAD` 的简短摘要）请用户确认。
- **先看全貌再读细节**：先跑 `git diff --stat`（含提交区间时补 `git log --oneline`），跳过 lockfile、编译产物、快照、二进制等噪音文件，聚焦真实逻辑与配置改动。
- **不止看 diff 片段**：对关键改动必须顺着入口、调用方、默认配置、功能开关和相关测试读上下文，核实改动在哪些场景真正生效。存在合并提交、冲突标记、被截断的超大 diff 或缺少下游仓库代码时，直接标明依据缺口，不要猜。

## 2. 按功能归并，排查隐性影响

- **按任务/能力命名**：先回答"这批改动合起来改变了什么事"，用业务或使用场景命名（如"离线环境启动插件"、"找回未提交草稿"），禁止按文件名、模块名或 `feat/fix` 提交类型平铺。
- **合并同源、拆分异构**：同一能力横跨界面、接口、存储、配置时合并成一项；同一处公共改动（公共组件、工具函数、默认配置、共享样式）波及多个入口时列清受影响的入口，各入口结果不同再拆开。
- **核实真实生效条件**：新增、删除、改名或受开关控制的能力，确认用户实际能否触达；加了开关但默认关闭的，明确标出"默认不生效"。
- **必查六类隐性影响**（只报告确实命中的项，没命中不凑数）：
  - **存量兼容**：持久化数据、本地缓存、配置文件、数据库结构变化后，老用户升级或已有数据会不会失效。
  - **默认值与优先级**：默认行为改变、配置项废弃、回退顺序调整。
  - **公共扇出**：共享模块改动波及的其他页面、平台（多端/多系统）、主题或语言。
  - **对外契约**：API、消息协议、CLI 参数、事件格式、错误码或导出接口变化。
  - **运行环境与依赖**：新增联网要求、权限、外部工具、构建/打包产物或跨平台差异。
  - **生命周期与降级**：初始化时机、缓存失效、并发重入、失败兜底路径。

## 3. 逐项评估（事实与风险分开）

每项影响聚焦四个问题：

- **谁受影响**：区分角色与前提（新用户 / 存量升级用户 / 特定入口、平台或配置 / 下游调用方 / 发布与运维）。
- **以前 → 现在**：同一场景下旧结果与新结果的对照，写可观察的结果，不写实现步骤。
- **收益与代价**：明确得到什么具体结果（如"重开页面保留草稿"，不写"体验更好"），以及确定失去的能力或增加的成本（多一步操作、增加联网依赖、兼容范围收窄等）。
- **潜在风险**：必须写**触发条件 + 具体后果**。已确定发生的属于代价/取舍，满足特定条件才触发的属于风险，两者不要混；禁止写"可能影响稳定性""注意边界情况"这类空话。

**证据纪律**：代码可直接证实的行为直接陈述事实，不加"预计""可能"；依赖运行时数据、外部服务或未读到的下游才能确认的结论，才标明前提或写"待验证"。不为了填满栏目虚构收益或风险。

## 4. 按意图组织输出

用中文，或跟随用户指定的语言。结论先行，按影响程度从高到低排列（**破坏性/存量兼容 > 核心高频路径行为变化 > 新能力/低频边界 > 内部调整**）。

### 默认输出（评估影响 / 看懂改动）

1. **一句话总览**：点明分析范围、影响最大的功能或风险，以及最受关注的人群/入口。
2. **影响明细**：
   - 多项功能变化用紧凑表格，每项一行，每格一两句短语：

     | 功能与影响范围 | 以前 → 现在 | 收益与代价 | 潜在风险 |
     |---|---|---|---|
     | 功能名 · 受影响人群或入口 | 同场景旧结果 → 新结果 | 得到什么；代价/取舍（无则写"无明显代价"） | 触发条件及后果（无则写"未见明显风险"） |

   - 只有 1 项功能变化，或单项存在多条复杂分支影响时，改用项目符号展开，不硬塞单行宽表。
3. **无行为变化项**：纯测试、格式化、注释、内部重构合并成一句带过，交代已确认无对外影响即可。
4. **重点验证**（有风险、存量兼容点或未覆盖路径时输出）：只列会改变发布判断的项，每条给最短验证路径（前置状态 + 一次操作/命令 + 预期结果）。

### 特定意图适配

- 用户问**"要回归哪些"**：简述变更后，把篇幅集中在按风险排序的回归清单（区分必测主路径、存量升级路径、异常/降级路径）。
- 用户问**"怎么写发布说明"**：直接输出面向用户的变更说明（新增 / 调整 / 修复 / 破坏性变更与迁移提示），不附内部风险表。

不要贴文件清单、函数名、代码片段和逐行走读；用户追问细节时再补。

## 5. 交付前自检

- [ ] 分析基于真实差异与调用上下文，已跳过噪音文件，没有靠猜补齐缺口
- [ ] 按功能/场景归并并按影响从大到小排序，没有按文件或提交流水账罗列
- [ ] 存量兼容、默认值、公共扇出、外部依赖等隐性影响已逐一排查
- [ ] 确定事实直接下结论，每条风险都有具体触发条件和后果，没有空话或重复表述
- [ ] 没有夹杂文件路径清单、函数名堆砌和代码走读
