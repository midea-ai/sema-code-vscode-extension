# 按功能梳理改动影响

## 1. 确认分析范围

- 用户指定了范围就以用户为准：分支对比（`main...HEAD`）、提交区间（`HEAD~5..HEAD`）、某个 tag、PR 基线，或只看暂存区（`git diff --cached`）。
- 没指定时在仓库根目录跑 `git status --short --untracked-files=all`，默认以 `HEAD` 为旧版、当前工作区为新版：`git diff HEAD` 看已跟踪文件的最终差异，未跟踪的新文件直接读内容。
- 工作区干净又没有指定区间时，直接说明没有可分析的改动，不要凭空推测。
- 暂存与未暂存的改动相互抵消时，按最终行为报告；首次提交前以空仓库为基线。
- 范围内存在合并提交、冲突标记，或只有状态清单没有实际内容时，说明对应结论的依据缺口，不要猜。

## 2. 归并成功能

- 先回答"这些改动合起来是为了让用户做成哪件事"，用任务命名（如"找回未提交的草稿"），不要用模块名、文件名或提交类型当标题。
- 同一任务横跨界面、服务、存储、配置时合并成一项。同一处公共改动（公共组件、工具函数、默认配置）影响多个入口时，列清受影响的入口；各入口行为不同再拆成两项。
- 顺着入口、调用位置、默认配置、开关和相关测试，核实改动在哪个场景真正生效。新增、删除、改名、加开关的功能要确认用户实际能不能用到；加了开关但默认关闭的，明确写"默认不生效"。

## 3. 逐项说清影响

每项至少回答五件事：

- **谁受影响**：哪类用户、哪个入口或哪段使用场景。
- **以前 → 现在**：同一个场景下旧结果与新结果的对照，写可观察的结果，不写实现细节。
- **得到什么**：用户多拿到什么，写具体结果（"重开页面后能继续编辑"），不写"体验更好"。
- **失去什么**：确定失去的能力，或确定增加的成本（多一步操作、多一条配置、兼容性范围收窄）。
- **哪里可能出问题**：触发条件加可能后果。已经发生的是取舍，要满足条件才发生的是风险，两者不要混。

只从代码推断出的结论用"预计""可能"；没有依据判断的维度写"待验证"。不要为了填满表格虚构收益或风险。

## 4. 输出

用中文，或跟随用户指定的语言。先用一句话点出影响最大的功能、涉及的人群或入口，再按影响从大到小排列。

行为变化用表格，每项一行，每格一句短语：

| 功能与影响范围 | 以前 → 现在 | 提升 | 取舍 | 潜在风险 |
|---|---|---|---|---|
| 功能名 · 人群或入口 | 同一场景下的旧结果 → 新结果 | 用户多得到什么 | 确定失去的能力或增加的成本 | 触发条件及可能后果 |

某维度经对照没有明确变化时，写"未见明显取舍"这类简短结论，不要留空。

## 5. 收尾

- 纯测试、格式化、内部重构合并成一句，交代能确认的影响即可。
- 只有会改变发布或验证判断的疑点才在末尾单列，每条给出最短验证场景（一条命令、一个页面、一次操作）。
- 不要贴文件清单、函数名、代码片段和逐行走读；用户要细节再补。
